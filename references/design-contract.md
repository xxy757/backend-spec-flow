# Mermaid 与 OpenSpec 的设计契约

在形成或修改设计时读取。按功能复杂度组织文档，不强制复制整套目录或所有图类型。

## 两张必需视图

### 业务流程图

使用 `flowchart`，让用户能回答：谁触发、先做什么、在哪里判断、条件是什么、最后发生什么。

- 为节点使用稳定 ID，如 `B_SUBMIT`、`B_VALIDATE`、`B_SAVE`，文案改变时尽量保留 ID。
- 判断边写具体条件，避免只有“检查”“处理”而无业务含义。
- 画出需求已定义的成功和失败出口；不要凭空补偿、重试或兜底。
- 将跨模块调用表示为职责清晰的步骤，不画每个内部函数。

### 数据流图

同样使用 `flowchart`，但按数据来源、处理节点、存储和使用方组织；不要只复制业务流程图并改标题。

- 连线标注实际传输的数据或对象，例如“创建请求”“已校验字段”“订单记录”“响应 DTO”。
- 标明读取和写入的方向；区分外部输入、处理中间数据、持久化记录与输出。
- 在转换节点标明相关操作，例如字段映射、过滤、聚合或格式转换。
- 标明影响本次功能的数据丢弃、更新或存储副作用；无数据库写入就如实画出，不为完整性添加存储。
- 表达逻辑实体名，不填入真实凭据、账号或敏感样本。

业务节点和数据处理节点可以使用不同 ID，在规格或验收记录中关联两者。

## 按需补充的视图

| 图 | 使用条件 | 必须表达 |
| --- | --- | --- |
| `sequenceDiagram` | 跨模块、异步或外部交互 | 实际参与者、调用顺序、关键请求响应；仅在设计包含时表达超时或重试 |
| `stateDiagram-v2` | 状态及其转换具有业务意义 | 状态、触发事件、转换条件、终态；规格补充非法转换的预期行为 |
| `erDiagram` | 新增或修改持久化实体关系 | 本次相关实体、关键字段、主外键及基数；精确类型和约束以 schema 与规格约定为准 |

图之间保持一致：时序图不能额外出现未约定的交互，状态图不能额外出现实现自行引入的状态，ER 图应与目标数据模型一致。外部失败或并发要求只在本次业务需要时细化，不机械添加全套容错机制。

## OpenSpec 应记录什么

沿用 OpenSpec 的 proposal、design、specs、tasks 职责。本 Skill 的 backend-diagram-flow schema 提供固定模板；使用已有 schema 时遵循其实际模板并补齐本 Skill 要求。文件职责如下：

- proposal.md 写目的与范围；design.md 集中放图、技术决策、最小实现约束和设计确认记录。
- specs/<capability>/spec.md 写可观察行为及场景；不把内部函数名、类层级写成行为规格。
- tasks.md 写步骤；verification.md 写实际证据。图、规则、任务之间用相对链接和稳定标识关联。

具体内容：

- **范围**：目标、非目标及本次涉及的已有能力。
- **图入口**：业务流、数据流和适用的补充图的源文件或文档锚点。
- **接口契约**：本次输入输出、必填或移除字段、错误结果及适用的现有鉴权要求。
- **业务与数据规则**：条件、状态、副作用、实体约束；有原子性要求时明确事务范围。
- **最小实现约束**：具体列出本次不需要的机制，避免“提高健壮性”等模糊任务成为扩大设计的理由。
- **节点不变量**：每张图后附不变量表，图中每个带业务规则的分支节点或判断边一行：允许条件、禁止行为（MUST NOT）、精确错误码或状态。图表达路径走向，表承载约束；不允许只靠图节点标签承载规则。
- **裁定精度**：技术决策逐条编号，每条含裁定结论、精确标识符（错误码、状态值、字段、事件名、file:symbol 锚点）、禁止项、对应图节点或场景；一条裁定至少一个可测试禁令和一个精确标识符。「沿用既有 X」必须带锚点与一句不变式，使沿用可被 diff 审查。specs 保持行为级、不写内部函数名的规则不变，锚点精度由 design 裁定承担，不得两边都省略。
- **验收场景**：使用该项目的 Requirement/Scenario 或等效结构，写出触发条件、行为和可观察结果。
- **测试矩阵**：设计阶段给出场景×层级×断言要点；验收场景回答“系统做什么”，测试矩阵回答“怎么证明”。
- **追踪关系**：场景连接图中路径；verification 对应表的需求／场景、图节点、预期实现锚点列在设计阶段建骨架，开发后补实现与实际测试证据。

只写当前阶段已知事实；未确定的业务选择单独标记，不伪装为已批准需求。测试尚未运行时写“未运行”，不预填“通过”。

## 层级与变更

图过大时按“系统 → 业务域／模块 → 功能 → 细节视图”拆分。使用 Markdown 相对链接作为基本导航；渲染器支持时可增加 Mermaid 节点链接，但不能假设所有阅读器支持点击。

change 中拆分的图默认放 diagrams/*.md，由 design.md 作为入口。HTML 预览由这些 Markdown 派生，标明源文件；业务变更必须回到源文件修改并重新生成预览。不要把渲染器的可点击性当作规格正确性或代码验收证据。

同一概念使用统一名称；图、Spec 和代码含义变化时一起审查差异。已存在的流程未改变时引用原图，不为小改动复制整套系统地图。正式图谱表示当前有效设计，change 中的目标设计应标明待实现状态，不能提前把未完成能力展示为已经运行。
